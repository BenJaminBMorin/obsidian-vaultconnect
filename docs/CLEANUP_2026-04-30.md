This document hands off the plugin-side findings from the
[2026-02-26 code review](../../vault-sync/docs/CODE_REVIEW_2026-02-26.md)

## Open Items (in priority order)

### MEDIUM

#### P6 — Conflict fallback stores remote hash as `localHash`
- **File**: `src/services/ConflictService.ts` (search for `localHash: remoteFile.hash`)
- **Issue**: When the conflict-creation fallback path runs, it writes the
  remote file's hash into the `localHash` field of the conflict record.
  Misleading at a minimum; could cause incorrect state if any consumer
  later trusts that field.
- **Fix**: Compute the actual local hash in the fallback path (same
  binary-aware logic used in `checkFileConflict`).

#### P7 — `SyncQueueService` busy-polls with `sleep(100)`
- **File**: `src/services/SyncQueueService.ts`
- **Issue**: A tight loop polling every 100ms drains battery on mobile
  and wakes the CPU constantly even when nothing is happening.
- **Fix**: Replace the polling loop with event-driven dequeue (signal
  when an item is enqueued; wait on the signal between drains).

#### P8 — `FileWatcher` emits delete without checking `ignoredPaths`
- **File**: `src/services/FileWatcherService.ts`
- **Issue**: Other operations honor the ignore set via `ignorePath` /
  `unignorePath`, but the delete handler skips that check. Deletions
  triggered by sync itself can echo back as user-initiated deletes,
  causing a sync loop of the same kind P4 fixed for downloads.
- **Fix**: Mirror the existing ignored-path guard from the create/
  modify handlers in the delete handler.

#### P9 — `locallyDeletedFiles` set grows unboundedly
- **File**: `src/services/SyncService.ts`
- **Issue**: The set tracking files deleted locally is appended to
  but never pruned. Over time it accumulates indefinitely, slowing
  down membership checks and bloating `data.json`.
- **Fix**: Prune entries after the corresponding tombstone is
  acknowledged by the server (or after a TTL like 30 days, since
  the server's deletion-tracking endpoint will keep returning the
  same tombstone for that long).

#### P10 — `fileHashes` and `lastSyncTimestamps` never pruned of deleted files
- **Files**: `src/services/FileSyncService.ts`,
  `src/services/ConflictService.ts`
- **Issue**: When a file is deleted (locally or remotely), its entry in
  these two persistent maps is left behind. Long-lived vaults
  accumulate stale entries that bloat `data.json`.
- **Fix**: Add a delete-from-map call in the deletion handlers; or run
  a periodic compaction that removes entries whose paths no longer exist
  in the vault and aren't in the active tombstone set.

#### P11 — EventBus listeners in `SyncService` constructor never removed
- **File**: `src/services/SyncService.ts`
- **Issue**: The constructor wires multiple `eventBus.on(...)` listeners
  but the `onunload` handler doesn't unwire them. If the plugin is
  reloaded (settings change, dev hot-reload) without a full Obsidian
  restart, listeners accumulate and old SyncService instances linger.
- **Fix**: Capture the unsubscribe handles, store them on the instance,
  and call them all in `onunload` / a `dispose()` method.

#### P12 — `hasRemoteChanges` masks network failures as "no changes"
- **File**: probably `src/services/SyncService.ts` or `FileSyncService.ts`
- **Issue**: If the API call to check for remote changes fails (timeout,
  401, network unreachable), the helper returns `false` like a clean
  "no changes" response. This hides errors and can stall sync silently.
- **Fix**: Distinguish failure from "no changes" — return a discriminated
  result (`{ hasChanges: boolean }` vs throwing) and surface failures to
  the caller, which should bubble them to the user via
  `ErrorNotificationService`.

#### P13 — `onunload` doesn't clean up all timers/listeners
- **File**: `main.ts`
- **Issue**: Several `setInterval` timers, document event listeners,
  and EventBus subscriptions are created in `onload` but not torn down
  in `onunload`. Reload-during-development causes dangling timers that
  fire against a dead plugin instance.
- **Fix**: Audit every `setInterval`, `addEventListener`, and
  `eventBus.on` call in `onload` and pair each with a teardown in
  `onunload`. Consider using `this.registerInterval` / `this.registerDomEvent`
  (Obsidian's plugin API helpers that auto-unregister).

## Suggested Order

Tackle MEDIUM in this order (cheapest-to-highest-impact ratio first):

1. **P11 + P13 + P16 + P17** — listener/timer cleanup. All
   constructor-wires-without-teardown bugs. One sweeping audit can
   close all four with the same pattern (`this.register*` helpers).
2. **P10 + P9** — pruning the persistent maps. Both have the same
   shape: tie-cleanup-to-deletion.
3. **P12** — failure detection. Highest user-impact in the MEDIUM tier
   (silent stalls are confusing).
4. **P7** — battery saver. Medium effort, real mobile impact.
5. **P8** — sync-loop guard. Low risk, mirrors P4's pattern.
6. **P6** — `localHash` fix. Smallest, easiest to ship.

LOW items can be tackled as a single grab-bag PR, or queued as
"clean up while you're in this file" tasks for whoever's next in each
service.
